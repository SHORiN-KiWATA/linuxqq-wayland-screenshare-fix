## 1. 它是什么

一个 `LD_PRELOAD` 注入库 `libqq-wl-portal.so`，加一个启动脚本 `linuxqq-wayland-fix`。

作用：让 QQ **自带的** Wayland 屏幕采集代码真正工作起来。QQ 里本来就有一套基于 portal + PipeWire 的采集实现，但缺一个「共享源选择器」，从来没被启用。本库替 QQ 补上这个选择器。

效果：

- 点共享 → QQ 自己的选窗 → niri 弹出 portal 选择框 → 对方看到画面；
- 画面数据直接从 niri 经 PipeWire 进入 QQ 的采集线程，不再像「截屏中转」类方案（如 qq-wayland-screenshare）那样在进程之间整帧搬运；
- QQ 主进程 CPU 从 70~96% 降到约 4%。

## 2. 背景：QQ 里那套没接上线的 Wayland 共享

### 2.1 QQ 屏幕共享的结构

```
QQ 主进程（Electron 界面，wrapper.node）
 └─ ppapi 子进程（音视频插件）
     ├─ libAVSDKPlugin.so   ← 音视频 SDK：会话、编码、网络。它决定「共享哪个屏幕」
     └─ broadcast-core.so   ← 采集库：真正去拿屏幕画面
```

`broadcast-core.so` 位于 `~/.config/QQ/versions/<版本>/avsdk/`，由 `libAVSDKPlugin.so` 用 `dlopen(..., RTLD_NOW)` 加载（没有 `RTLD_DEEPBIND`，所以 `LD_PRELOAD` 能拦到它调用的函数）。

### 2.2 broadcast-core 里的两条采集路径

反汇编 `broadcast-core.so` 后得到下面这些事实，地址对应 3.2.34：

**判断函数** `IsWayland`（0x5c9d0）：

```c
int IsWayland(void) {
    const char *t = getenv("XDG_SESSION_TYPE");
    return t && strcmp(t, "wayland") == 0;
}
```

**入口** `MonitorCapture_CaptureDisplay`（0x510a0）：

```c
if (IsWayland()) {
    uint64_t h = capture->handle;            // 上层传来的 64 位「显示器句柄」
    capture->pw_fd   = (uint32_t)h;          // 低 32 位 → +0x1f0
    capture->pw_node = (uint32_t)(h >> 32);  // 高 32 位 → +0x200
    启动线程 MonitorCapture_WaylandProc;
} else {
    启动线程 MonitorCapture_X11Proc;          // XShmGetImage / XGetImage 截根窗口
}
```

**Wayland 采集线程** `MonitorCapture_WaylandProc`（0x51210）：

1. 用自家的 `DllGetFuncByName` 加载 `libpipewire-0.3.so`，然后**用 `dlsym` 逐个取出 21 个 `pw_*` 函数**放进函数表（`pw_init`、`pw_context_connect_fd`、`pw_stream_connect`……）；
2. `pw_context_connect_fd(ctx, capture->pw_fd, ...)` 连上 portal 给的 PipeWire 远端；
3. `pw_stream_connect(stream, INPUT, capture->pw_node, ...)` 连上那路画面；
4. 在 `OnStreamProcess` 回调里取帧 → 上传 OpenGL 纹理 → 交给编码。

**本该负责填句柄的选择器** `CaptureSelector_DoModal` / `CreateProc` / `StartProc`：里面有完整的 portal 调用（`CreateSession`、`SelectSources`、`Start`、`OpenPipeWireRemote`），拿到 fd 和 node id 后打包成句柄。

### 2.3 断在哪里

- **没有任何代码调用 `CaptureSelector`**：broadcast-core 内部没有引用，`libAVSDKPlugin.so` 里也找不到相关字符串。
- 上层（`libAVSDKPlugin.so`）在 Wayland 下直接拒绝：`IsScreenShareEnvAvailable` 用它自己的 `util::IsWayland()`（同样是看 `XDG_SESSION_TYPE`）判断，界面就弹出「Wayland桌面环境暂时无法使用屏幕分享功能」。
- 就算绕过界面，上层传给 broadcast-core 的也是 X11 显示器编号（实测为 `1`）。Wayland 分支会把它当成「fd=1、node=0」去连 PipeWire，什么也连不上。

结论：**采集这一半已经写好，选择器那一半没接上线。**

## 3. 工作原理

### 3.1 三处拦截

| # | 拦截什么 | 仅对谁生效 | 做什么 |
| --- | --- | --- | --- |
| 1 | `getenv("XDG_SESSION_TYPE")` | 调用方在 `broadcast-core.so` 里 | 返回 `"wayland"`，让它走 Wayland 分支。QQ 其余部分仍看到 `x11`，界面不拦截 |
| 2 | `dlsym(handle, "pw_...")` | 调用方在 `broadcast-core.so` 里 | 取 `pw_context_connect_fd` / `pw_stream_connect` / `pw_core_disconnect` 时，返回本库的包装函数 |
| 3 | 上面三个包装函数 | — | 自己走一遍 portal，把真的 fd、node id 换进去；结束时关闭 portal 会话 |
| 4 | `pa_context_get_sink_info_by_name` / `pa_context_get_source_info_by_name` | 调用方在 `broadcast-core.so` 里 | 把设备采样格式改报为 FLOAT32LE，让「共享设备音频」能启动（见 3½ 节） |

### 3.2 一次完整的共享

```
用户点「确定」
  │
  ▼
libAVSDKPlugin（以为是 X11）→ 把显示器编号 1 作为句柄交给 broadcast-core
  │
  ▼
broadcast-core: IsWayland()
  └─ getenv("XDG_SESSION_TYPE") ──拦截①──→ "wayland"
  │
  ▼
MonitorCapture_WaylandProc
  ├─ dlsym("pw_context_connect_fd") ──拦截②──→ wrap_connect_fd
  ├─ dlsym("pw_stream_connect")     ──拦截②──→ wrap_stream_connect
  ├─ dlsym("pw_core_disconnect")    ──拦截②──→ wrap_core_disconnect
  │
  ├─ wrap_connect_fd(ctx, fd=1)  ──③──┐
  │     丢弃 fd=1（它不是 fd！）        │
  │     CreateSession                  │
  │     SelectSources（屏幕+窗口）      │   D-Bus → xdg-desktop-portal → niri
  │     Start ──→ niri 弹出选择框，用户选 │
  │     OpenPipeWireRemote → 真 fd      │
  │     真 pw_context_connect_fd(真 fd) ◄┘
  │
  ├─ wrap_stream_connect(target=0) → 换成 Start 返回的 node id → 真 pw_stream_connect
  │
  ├─ （之后完全是 QQ 自己的代码：收帧 → GL → 编码 → 发送）
  │
  └─ 共享结束：wrap_core_disconnect → 真 pw_core_disconnect → Session.Close
```

### 3.3 为什么拦 `dlsym` 而不是直接定义同名的 `pw_*` 函数

broadcast-core 是先 `dlopen("libpipewire-0.3.so")`，再 `dlsym(那个句柄, 名字)`。用句柄查找只搜那个库和它的依赖，**不搜 LD_PRELOAD 的库**，所以直接定义 `pw_context_connect_fd` 不会生效，只能在 `dlsym` 这一层截。

## 3½. 共享电脑声音（设备音频）

### 现象

共享工具栏点了「共享设备音频」，对方仍然听不到电脑里播放的声音；界面上没有任何报错。

### 排查过程

用 `gdb` 在 ppapi 进程里挂只打印、不暂停的探针（`dprintf`），观察切换按钮时的调用：

```
ConfigureShareAudio(…, enable=1)       ← 界面命令到了
EnableShareAudio(enable=1, 2, 48000, 16)
InitAudioCapture enter
  bc AudioMixer_Init
  bc AudioCapture_Init                 ← broadcast-core 的系统声音采集
  bc AudioCapture_EnumDevice           ← 找默认输出设备
  audio_capture_->Init returned 0x80004001   ← E_NOTIMPL
  EXIT: audio_capture_ init fail
EnableShareAudio(enable=0, …)          ← QQ 悄悄把它关掉了
```

### 原因

反汇编 `AudioCapture_Init`（broadcast-core，0x4af60）：

```c
查询默认输出设备的 sample_spec → format, rate, channels
if (format == 0 || rate == 0)               return E_NOTIMPL;
if (format != PA_SAMPLE_S16LE /*3*/ &&
    format != PA_SAMPLE_FLOAT32LE /*5*/)    return E_NOTIMPL;
// 然后按同样的格式 pa_stream_connect_record 录这个设备的 .monitor
```

QQ 只支持 16 位整数或 32 位浮点格式的输出设备。很多板载声卡（ALSA 设备）的原生格式是 **s32le**（格式 7），于是直接失败。这和 Wayland 无关，「截屏中转」类方案下同样存在。

### 修法

拦截 broadcast-core 调用的 `pa_context_get_sink_info_by_name` / `pa_context_get_source_info_by_name`，在结果回调里把 `sample_spec.format` 改成 FLOAT32LE 再交给 QQ。QQ 随后按 FLOAT32LE 去录 `.monitor`；**录音端可以要求任意格式，PipeWire 会自动转换**，所以对声音没有影响。

实现上的两个坑：

1. **回调要包一层**：原回调和原 userdata 存进一个小结构，用自己的 trampoline 回调，复制一份 `pa_sink_info`、改格式后再调用原回调；`eol` 时释放。
2. **真函数要从 libpulse 里直接取**：libpulse 是作为 broadcast-core 的依赖被 `dlopen` 进来的（局部作用域），`dlsym(RTLD_NEXT, …)` 找不到它，返回 NULL，一调用就崩。改成 `dlopen("libpulse.so.0", RTLD_NOLOAD)` 再 `dlsym`。本库也不链接 libpulse，不会给其它进程增加依赖。

正常时日志里会出现：

```
device audio: report sample format 7 as float32le (5) to broadcast-core
```

如果你的输出设备本来就是 s16le / f32le，这行不会出现，也不需要它。

## 4. 代码逐段讲解

### 4.1 判断调用方

```c
static int from_broadcast_core(const void *caller)
{
    Dl_info info;
    if (!dladdr(caller, &info) || !info.dli_fname) return 0;
    const char *base = strrchr(info.dli_fname, '/');
    return !strcmp(base ? base + 1 : info.dli_fname, "broadcast-core.so");
}
```

- `__builtin_return_address(0)` 拿到「谁调用了我」的代码地址；
- `dladdr` 查这个地址属于哪个 `.so`；
- 只认 `broadcast-core.so`，其它库的调用一律原样放行。

`dlsym` 的情况：broadcast-core 里的 `XGetProcAddress` 是一条 `jmp dlsym@plt`（尾跳转），所以 `dlsym` 看到的返回地址落在 broadcast-core 的 `DllGetFuncByName` 里，判断成立。

### 4.2 getenv

```c
char *getenv(const char *name)
{
    if (name && !strcmp(name, "XDG_SESSION_TYPE") &&
        from_broadcast_core(__builtin_return_address(0)))
        return (char *)"wayland";
    return name ? lookup_env(name) : NULL;
}
```

`lookup_env` 自己遍历 `environ`，不再转发给 glibc 的 `getenv`，避免任何递归或初始化顺序问题。

### 4.3 dlsym 与 musttail

```c
void *dlsym(void *handle, const char *name)
{
    if (!real_dlsym) resolve_dlsym();
    if (name && !strncmp(name, "pw_", 3) &&
        from_broadcast_core(__builtin_return_address(0)))
        return intercept(handle, name);
    __attribute__((musttail)) return real_dlsym(handle, name);
}
```

要点：

- **真 dlsym 从哪来**：`dlvsym(RTLD_NEXT, "dlsym", "GLIBC_2.34")`（找不到就退回 `GLIBC_2.2.5`）。`dlvsym` 没被拦截，所以不会递归。
- **为什么懒加载**：其它库的构造函数可能比本库的构造函数更早调用 `dlsym`。
- **为什么必须尾调用**：glibc 的 `dlsym` 用返回地址判断调用者是谁，`dlsym(RTLD_NEXT, ...)` 的语义就靠它。如果写成普通调用，glibc 会以为调用者是本库，别的库的 `RTLD_NEXT` 查找就会出错。`musttail` 强制编译成 `jmp`，栈上的返回地址仍然是原调用者。编译后可用 `objdump -d libqq-wl-portal.so | awk '/<dlsym>:/,/^$/'` 确认里面有 `jmp *%rdx`。GCC 15 起支持 `musttail`。

### 4.4 portal 请求的通用函数 `portal_request`

portal 的 `CreateSession` / `SelectSources` / `Start` 都是异步的：方法本身立即返回一个 Request 对象路径，真正的结果稍后通过该路径上的 `Response` 信号送来。

做法：

1. 自己生成 `handle_token`，按规范预测出 Request 路径：
   `/org/freedesktop/portal/desktop/request/<发送者唯一名，去掉冒号、点换成下划线>/<token>`；
2. **先订阅**这个路径的 `Response` 信号，**再调用**方法，避免信号先到而错过；
3. 在一个**本线程私有的 `GMainContext`** 里跑循环等待，不干扰 QQ 自己的事件循环；
4. 带超时：`Start` 等 300 秒（给用户在弹框里慢慢选），其余 30 秒；
5. `response` 为 0 表示成功，1 表示用户取消，2 表示其他失败。

### 4.5 `run_portal`：完整流程

| 步骤 | 方法 | 关键参数 | 取回 |
| --- | --- | --- | --- |
| 1 | `CreateSession` | `session_handle_token` | `session_handle` |
| 2 | `SelectSources` | `types=3`（屏幕+窗口）、`multiple=false`、`cursor_mode` | — |
| 3 | `Start` | parent_window `""` | `streams` 数组，取第一个的 node id |
| 4 | `OpenPipeWireRemote` | — | 通过 Unix fd 列表传回的 PipeWire fd |

`cursor_mode`：先读 `AvailableCursorModes` 属性（niri 返回 7），支持就用 2（光标画进画面），否则用 1（隐藏）。

### 4.6 D-Bus 连接必须常驻（踩过的坑）

```c
static GDBusConnection *bus(void)   // 进程内常驻一份 session bus 连接
```

**portal 会话绑定在发起请求的 D-Bus 连接上**，这条连接一断，portal 就认为请求方退出了，会立即收回会话。

第一版用 `g_bus_get_sync()` 拿到共享连接，用完就 `g_object_unref()`。ppapi 进程里没有别人持有这条连接，引用计数归零，连接随即关闭。结果是：niri 刚交出 node（日志 `delivering node id 195`），3 毫秒后就 `stop_cast`，QQ 的输入流一直处于 `suspended`，对方一直「正在加载」。

现在 `bus()` 在整个进程生命周期内持有连接，断了会自动重连。

### 4.7 三个包装函数

**`wrap_connect_fd`**

- 收到的 `fd` 其实是 X11 显示器编号的低 32 位（实测为 1），**绝不能交给 PipeWire**。`pw_context_connect_fd` 会接管这个 fd 并在结束时关掉它，传进去 1 就等于把进程的 stdout 关了。
- 跑 `run_portal()`，成功就用真 fd 调用真函数；
- 失败或用户取消时，创建一对 `socketpair`，关掉一端，把另一端交给 PipeWire。这样连接必然失败，QQ 走它自己的失败路径，不会崩；
- 记下 `active_core`、`active_session`、`active_node`。

**`wrap_stream_connect`**

- 把 `target_id`（实测为 0）换成 `active_node`。

**`wrap_core_disconnect`**

- 如果断开的是我们记录的那个 core，就清空状态，先调用真函数，再对 portal 会话调用 `Session.Close`。niri 收到后停止录屏。

## 5. 部署

见 [README](../README.md#安装)。安装后的文件：

| 路径 | 内容 |
| --- | --- |
| `/usr/bin/linuxqq-wayland-fix` | 启动脚本（含 `--doctor` 自检） |
| `/usr/lib/linuxqq-wayland-fix/libqq-wl-portal.so`（Fedora 为 `/usr/lib64/...`） | 注入库 |
| `/usr/share/applications/linuxqq-wayland-fix.desktop` | 应用菜单入口「QQ（Wayland修复版）」 |

启动脚本做的事：

| 设置 | 作用 |
| --- | --- |
| `LD_PRELOAD=…/libqq-wl-portal.so` | 注入本库 |
| `XDG_SESSION_TYPE=x11` | 让 QQ 界面和 libAVSDKPlugin 不拦截共享。broadcast-core 那边由本库单独改成 `wayland` |
| `MESA_SHADER_CACHE_DISABLE=true` | 绕开 QQ 自带 zstd 与 Mesa 的符号冲突（见 §7.4）。Wayland 路径同样会初始化 OpenGL，同样需要 |
| `--ozone-platform=wayland` | QQ 主窗口用原生 Wayland，与共享无关 |

### 关于 musttail 与汇编蹦床

最初的实现用 `__attribute__((musttail))` 让 `dlsym` 的转发成为尾调用，但这需要 GCC 15+。为了能在 Debian 12（GCC 12）和 Ubuntu 24.04（GCC 13）上编译，现在 x86_64 和 aarch64 改用汇编蹦床（`src/dlsym_trampoline.S`）：先调用 C 函数 `qqwl_dlsym_decide()` 判断要不要拦截，不拦截就恢复参数，再 `jmp` 到真正的 dlsym。其它架构仍然走 musttail。

## 6. 使用

1. **完全退出 QQ**，托盘里也要退出。检查：`pgrep -af '^/opt/QQ/qq --ozone'` 没有输出。
2. **Easy Effects 可以照常运行**，但它的排除名单里必须有 `TRAE`，QQ 麦克风选 **Easy Effects Source**（见 §7.4）。
3. 运行 `linuxqq-wayland-fix`。
4. 发起共享。QQ 先弹出**它自己的**选窗，随便选「桌面1」，点「确定」。这一步选什么不影响结果。
5. **niri 的选择框**弹出来，在这里选真正要共享的屏幕或窗口。
6. 全屏蓝框会出现并挡住屏幕。这是 QQ 为 X11 设计的覆盖层，本方案暂未处理。可以在 niri 里把它移到别的工作区，或者让它保持浮动。
7. 结束共享后，portal 会话会自动关闭。

想更流畅：第 5 步选单个窗口，别选整个屏幕。

### 7.2 检查 QQ 的视频流是否在跑

```bash
pw-dump | python3 -c '
import json,sys
for o in json.load(sys.stdin):
  i=o.get("info") or {}; p=i.get("props") or {}
  if p.get("node.name")=="qq" and "Video" in str(p.get("media.class")):
    print(o["id"], i.get("state"), (i.get("params") or {}).get("Format"))'
```

正常：`running`，格式类似 `BGRx 2560x1440`。如果是 `suspended` 并且 `Format []`，说明没收到画面。

### 7.3 检查 niri 有没有提前停止

```bash
journalctl --user --since '-5min' -o cat | grep -E 'delivering node id|stop_cast|StartCast'
```

`delivering node id N` 之后紧接着出现 `stop_cast`，说明 portal 会话被收回了，通常是 D-Bus 连接断了（见 4.6）。

### 7.4 QQ 自身的两个崩溃（与 Wayland 无关）

**Mesa 着色器缓存与 QQ 自带 zstd 冲突**：QQ 的 `libAVSDKPlugin.so` 静态打包并导出了 221 个 `ZSTD_*` 符号。共享时 broadcast-core 初始化 OpenGL，Mesa 读磁盘着色器缓存调用系统 libzstd，libzstd 内部经 PLT 的调用被 QQ 的同名符号截走，结构体不兼容，采集进程 SIGTRAP。调用栈：`VSync_Proc → glXChooseVisual → libgallium → libzstd ZSTD_decompress → libAVSDKPlugin ZSTD_decompressDCtx`。解决：`MESA_SHADER_CACHE_DISABLE=true`。

**Easy Effects 移动音频流引发竞态**：Easy Effects 会把新出现的流移到自己的设备上。QQ 音频模块收到「流被移动」后在采集线程里调用 `OnDefaultDeviceChanged` 重新枚举设备，与主线程的枚举并发。它枚举的写法是先把 `PulseAudioWrapper` 的成员指针（+0xe8 / +0xf8）指向调用方栈上的缓冲区，再等异步回调写入，两个线程同时这么做就会写坏内存，之后在 mars xlog 的 `realloc` 里被分配器检测到而 SIGTRAP。对照实验：Easy Effects 运行、虚拟设备存在，仅把 `TRAE` 加入它的输入/输出排除名单，即不再崩溃。解决：排除名单加 `TRAE`，QQ 麦克风选 Easy Effects Source。


### 7.5 共享窗口时画面斜切成条纹（QQ 的 bug，已修）

**现象**：共享单个窗口时，对方看到的画面挤在左侧，满是竖条纹、行重复。

**原因**：`OnStreamProcess`（broadcast-core 0x52af0）对共享内存帧：

```c
memcpy(pbo, buffer->datas[0].data, width * height * 4);   // 忽略 chunk->stride / offset
glTexSubImage2D(GL_TEXTURE_2D, 0, 0, 0, width, height, fmt, GL_UNSIGNED_BYTE, 0);
```

合成器给的每行常带填充（stride > width×4），宽度不规整的窗口尤其常见，于是逐行错位。DMA-BUF 分支会正确使用 stride，但 QQ 声明的格式里没有 modifier，合成器只会给共享内存帧。

**修法**：拦截 `pw_stream_add_listener`（额外挂一个监听器，从 `param_changed` 解析 `spa_video_info_raw` 得到宽高）、`pw_stream_dequeue_buffer`（帧有填充或偏移时重排成紧凑的一块，临时替换 `datas[0].data`）、`pw_stream_queue_buffer`（还帧前恢复原指针）、`pw_stream_destroy`（释放状态）。

**验证**：本地 PipeWire 生产者输出 1001×300、stride 4032 的帧，消费者放在名为 broadcast-core.so 的库里，按 QQ 的方式取帧并逐像素校验：不注入 0/90 帧正确，注入后 89/89 帧正确。

### 7.6 共享时 DRM GEM 无上限增长（QQ 的 bug，已修）

**现象**：Wayland 下共享整屏，ppapi 进程 `/proc/<ppapi>/fdinfo/*` 里的

```
drm-total-system0
```

单调增长、进程退出前不回收。4K 整屏约一分钟就涨到十几 GB（实测 13.7 GB，另有一次约 18.5 GB），最终把整机内存吃光。这些 GEM 以系统内存为背板、被内核 pin 住，没有用户态 fd、也不映射进地址空间，所以 `ps` / `top` / `smaps` 都看不到，只有 DRM fdinfo 和 cgroup 的 `shmem` 能看到。合成器那 8 个 `mutter-screen-cast-memfd` 缓冲数量是稳定的，不是 fd 泄漏。

**原因**：`OnStreamProcess`（broadcast-core 0x52af0）每帧都会重建采集用的上传纹理和 PBO，重建前它用两个字段做「尺寸没变就跳过」的判断：

```c
if (capture->frame_w != width || capture->frame_h != height) {   // +0x1f8 / +0x1fc
    glDeleteTextures(1, &capture->texture);                      // +0x204
    GL_InitTexture(width, height, fmt, ..., &capture->texture);  // glTexImage2D，宽×高×4
    if (datas[0].type != SPA_DATA_DmaBuf) {                      // 共享内存帧
        glDeleteBuffers(1, &capture->pbo);                       // +0x208
        glGenBuffers(1, &capture->pbo);
        glBufferData(GL_PIXEL_UNPACK_BUFFER, width * height * 4, NULL, GL_STREAM_DRAW);
    }
}
```

但这两个字段（`+0x1f8` / `+0x1fc`）在 3.2.34-53644 的整个库里**只被读、从未被写**（`objdump` 里只有 `cmp %r14d,0x1f8(%rbx)` 和 `cmp %r15d,0x1fc(%rbx)` 各一处，没有任何写指令），于是条件恒真：每帧删掉再新建一个宽×高×4 的纹理和一个同样大的 PBO。4K 下这是每帧两次 31.6 MB 的 DRM GEM 分配。

**修法**：QQ 把 MonitorCapture 对象本身作为 `pw_stream_add_listener` 的第四个参数（`data`）传进来，而这正是本库已经拦截的函数。在 `pw_stream_dequeue_buffer`（`OnStreamProcess` 就是通过它进到这里的，所以一定早于那段判断）里替 QQ 把「已分配的宽高」写回 `+0x1f8` / `+0x1fc`：尺寸没变就让 QQ 跳过重建，只在第一帧和尺寸真的变了的那一帧放行。

对象身份用 `capture+0x1d0` 处存的 `pw_stream` 指针确认（`OnStreamProcess` 开头就是 `mov 0x1d0(%rdi),%rdi` 再调 `pw_stream_dequeue_buffer`），对不上就什么都不做并在日志里报一行 `capture layout mismatch`。`QQ_WL_FRAME_REUSE_DISABLE=1` 可以关掉。

跳过了不该跳过的重建，代价远比多重建一次大：QQ 不检查 `glMapBuffer` 的返回值，会按新尺寸往旧的（或根本没建过的）PBO 里 `memcpy`。所以还有几道保险：

- **只对认得的代码生效**：`pw_stream_add_listener` 时，按 QQ 传进来的 `events->process`（即 `OnStreamProcess`）比对四条用到这些偏移的指令（`+0x11` 的 `mov 0x1d0(%rdi),%rdi`、`+0x11a`/`+0x123` 的两条 `cmp`、`+0x13c` 的 `mov 0x204(%rbx),%eax`），对不上就整个关掉，日志报 `unknown OnStreamProcess code`。
- **只在取到帧时处理**：`pw_stream_dequeue_buffer` 返回 NULL 时 `OnStreamProcess` 直接返回、不会重建；这时若记下「已按新尺寸重建」，下一帧就会跳过真正需要的重建。
- **每次重新协商都放行一次**：尺寸不变时格式也可能变，而建纹理用的格式、BGRx/BGRA 的 swizzle、要不要建 PBO（SHM 还是 DMA-BUF）都取决于它。
- **放行时把两个字段清零**：共享结束时 QQ 删掉纹理和 PBO（`+0x204`/`+0x208` 清零）但不动 `+0x1f8`/`+0x1fc`，同一个对象再共享一次同样尺寸时，留下的宽高会让 QQ 跳过重建、对 PBO 0 做 `glMapBuffer`。

**验证**：共享 3840×2160 整屏，日志出现

```
[qq-wl-portal pid=37649] reuse capture texture: 3840x2160 (skip per-frame glTexImage2D/glBufferData)
```

`renderD128` 的 `drm-total-system0` 停在约 191 MB（改之前同一阶段是 13.7 GB，且约每 8 秒涨 3 GB）。

## 8. 它到底有多「原生」：还涉及哪些 X11

| 环节 | 用的是 | 说明 |
| --- | --- | --- |
| 画面采集（niri → PipeWire → QQ） | **Wayland** | 不调用任何 X11 截屏函数，也不需要 XShm |
| 选择共享源 | **Wayland portal** | 由本库替 QQ 发起 |
| QQ 主窗口 | **Wayland** | `--ozone-platform=wayland` |
| QQ 自己的选窗缩略图 | X11 | `wrapper.node` 用 `XGetImage` 截，所以 Wayland 窗口和桌面显示为黑 |
| 共享进程的其它部分 | X11 | 实测共享期间 ppapi 对 XWayland 开着 2 条连接。可能来源：`eglGetDisplay()` 没指定平台，Mesa 默认走 X11；libAVSDKPlugin 仍在 X11 模式下枚举显示器（未逐一确认） |
| QQ 的整体判断 | X11 | 全程以为是 X11 会话，全屏蓝框也是按 X11 的方式建的 |

结论：**画面这条路是原生 Wayland，但 QQ 仍然需要 XWayland 才能完成共享**，X 只是被用来做些杂活。要彻底去掉 X，需要腾讯在界面层正式支持 Wayland。

## 10. 已知限制

1. **全屏蓝框不会自动隐藏**。
2. **依赖 QQ 未正式启用的内部实现**：`IsWayland()` 的判断方式、句柄的打包格式、PipeWire 函数的获取方式（`dlsym` 加函数名）。任何一个变了都会失效，而且多半不报错，只是没画面。
3. **只在 QQ 3.2.34-53644 + niri 上验证过**。其它桌面环境（KDE、GNOME、wlroots 系）理论上能用，因为都是标准 portal，而且 QQ 不接受 DMA-BUF，portal 会退回普通内存画面。但没有实测过。
4. **同一时间只支持一路共享**（全局状态只有一份）。QQ 本身也只允许一路。
5. **QQ 自己的选窗是摆设**：选什么都一样，以 niri 弹框里的选择为准。
6. QQ 自身的两个崩溃问题靠外部设置绕开：Mesa zstd 冲突（`MESA_SHADER_CACHE_DISABLE=true`），以及 Easy Effects 移动音频流引起的竞态（排除名单加 `TRAE`）。

## 11. QQ 更新后怎么重新确认能不能用

QQ 会悄悄热更新到 `~/.config/QQ/versions/<新版本>/`。更新后如果不能用了，按顺序检查：

```bash
V=$(ls -d ~/.config/QQ/versions/*/ | sort -V | tail -1)
B=$V/avsdk/broadcast-core.so
objdump -d --no-show-raw-insn $B > /tmp/bc.s

# 1. Wayland 采集路径还在不在
strings -a $B | grep -E 'MonitorCapture_WaylandProc|OpenPipeWireRemote'

# 2. IsWayland 是否还是「getenv + strcmp」的写法
awk '/<IsWayland>:/,/ret/' /tmp/bc.s | grep -E 'getenv|strcmp'

# 3. 句柄拆分方式：应能看到「右移 32 位、存 node、存 fd」三条指令
awk '/<MonitorCapture_CaptureDisplay>:/,/WaylandProc/' /tmp/bc.s | grep -E 'shr +\$0x20|0x1f0|0x200'

# 4. PipeWire 函数是否仍经由 dlsym 获取
strings -a $B | grep -E '^pw_(context_connect_fd|stream_connect|core_disconnect)$'
awk '/<XGetProcAddress>:/,/ret|jmp/' /tmp/bc.s | grep dlsym

# 5. 加载方式有没有加上 RTLD_DEEPBIND（0x8）。加了就拦不到；正常应该是 mov $0x2,%esi
objdump -d --no-show-raw-insn $V/avsdk/libAVSDKPlugin.so | grep -B3 'dlopen@plt>$' | grep esi
```

全部符合，就重新测一次共享；有不符合的，对照第 2 节的分析改代码。

## 附：剪贴板修复（`libqq-clipbridge.so`）

### 问题在哪

QQ 在 Wayland 下有两套剪贴板路径：

- **Chromium 网页内核自己的 Ctrl+C / Ctrl+V**：走 Wayland，正常；
- **QQ 自己的剪贴板代码**：右键「复制」、粘贴图片和文件等。实现在 `wrapper.node` 的 `ClipBoardHelper` 里，只用 Xlib（`XSetSelectionOwner` / `XConvertSelection` / `XGetSelectionOwner`），没有任何 Wayland 分支，所以只读写 X11 剪贴板。

QQ 窗口是原生 Wayland 窗口，不是 X11 窗口，XWayland（或 xwayland-satellite）不会帮它同步 X11 剪贴板，于是两边互不相通。浏览器 Ctrl+C 后粘贴进 QQ「时好时坏」，就是因为 QQ 有时用 Chromium 的粘贴（读 Wayland），有时用自己的粘贴处理（读 X11）。

这些剪贴板调用由 `major.node` 在 C++ 层直接发起，不经过 JS 层，所以没法在 JS 层改成调用 Electron 的剪贴板模块。

### 怎么桥接

注入库在 QQ 主进程里起一个后台线程，持有**自己的** X 连接和 Wayland 连接：

- **QQ 复制 → Wayland**：拦截 `XSetSelectionOwner`。QQ 取得 CLIPBOARD 后，线程向 QQ 要 TARGETS，再通过 data-control 在 Wayland 上提供对应的 MIME 类型；别的程序粘贴时才向 QQ 取那一种格式的数据（支持 INCR 分块）。
  - 文本：X11 的 `UTF8_STRING` 等映射为 `text/plain;charset=utf-8` 等；
  - 文件：QQ 给的是裸路径，转成 `file://` URI（`text/uri-list` 用 CRLF 分隔），并提供 `x-special/gnome-copied-files`；此时不提供 `text/html`（QQ 的 HTML 只是 `<img src=缓存路径>`，很多程序会优先选它而拿不到图）；
  - 复制图片而原图没有下载到本地时（路径指向不存在的文件），只提供 `image/png` 数据。
- **Wayland → QQ 粘贴**：data-control 的 `selection` 事件一到，线程用自己的 X 窗口接管 CLIPBOARD 并声明对应的 X11 TARGETS；QQ 粘贴时按需从 Wayland 读取，大数据走 INCR 分块发给 QQ。`text/uri-list` 也以 `x-special/gnome-copied-files` 提供给 QQ。
- **防回环**：自己写到 Wayland 的内容附带私有格式 `application/x-qq-clipbridge`，收到带这个格式的 `selection` 时忽略；接管 X11 时，TARGETS 里也带上这个格式。
- **不抢 X11 程序的剪贴板**：X11 程序（如 Typora、CodeBuddy 这类跑在 XWayland 下的 Electron 程序）复制时，xwayland-satellite / KWin / wlroots 会把它同步到 Wayland（satellite 一次复制可能同步两次）。这次 Wayland 变化不能当成「别的程序复制了」去接管 X11，否则合成器又把我们同步回 Wayland，来回循环，大家都读不到内容。用 XFixes 记下每次 X11 程序（包括 QQ 自己）设置 CLIPBOARD 的时间，1.5 秒内、且它仍是主人时到来的 Wayland 变化都视为同步；格式里有 `TIMESTAMP` / `TARGETS` / `MULTIPLE` 这类 X11 才有的名字时也是。主人若是合成器自己的代理窗口（用 XRes 查出所属进程：合成器本身或 `xwayland-satellite`），照常接管。
- **已经是主人时不重复接管**：每次换主人，satellite、fcitx5、Steam 等监听 X11 剪贴板的程序都会来读，fcitx5 还会把文字写回 Wayland。已经持有 X11 剪贴板时只更新内容，不再 `SetSelectionOwner`，避免这种来回。
- **启动时**：连上 Wayland 会先收到一次「当前剪贴板」；如果此时 X11 剪贴板已经有主人（比如 QQ 刚复制过），不去抢。

### 协议与兼容

- 优先 `ext-data-control-v1`，没有时退回 `wlr-data-control-unstable-v1`。两者的请求和事件完全一致，只有创建对象（`create_data_source`、`get_data_device`）需要区分协议，其余调用共用一套代码。
- KDE Plasma（KWin）自己会同步 XWayland 的剪贴板与 Wayland，叠加本桥会互相抢所有权并导致 QQ 崩溃；KDE 会话下启动器默认不预加载本库（日志头部 `clipboard=off(kde)`），QQ 的 X11 剪贴板由 Plasma 自己桥接。`QQ_CLIPBOARD_FIX_FORCE=1` 可强制启用（仅供测试）。
- GNOME 两种都不支持，剪贴板修复在 GNOME 上不可用。
- QQ 以 X11 方式运行时（命令行最后一个 `--ozone-platform=` 为 `x11`，或没有该参数时 `--ozone-platform-hint` / `ELECTRON_OZONE_PLATFORM_HINT` 为 `x11`）不启用：此时 QQ 窗口是 X11 窗口，XWayland 自己会同步剪贴板。

### 与外部同步工具（如 linuxqq-clipsync）的比较

外部工具在**每次**剪贴板变化时都要把内容完整读出、再写到另一边（多次启动 xclip / wl-paste 等进程），且只能同步一种格式，同步完成前有空窗期。本库只在变化时交换格式列表，粘贴时才传数据、只传一次，保留全部格式，另一侧几乎立即可用，且只在 QQ 运行期间存在。

## 附：共享时防闪退（窗口几何为空）

显示器坐标不从 0 开始时（如 Hyprland 单屏 `position=1920x0`），点「确定」开始共享 QQ 会闪退（#1，由 [@YoungJurry](https://github.com/YoungJurry) 在 #2 中最早定位）。

崩溃点在 QQ 主程序里 Chromium 的 Wayland 后端：发 `xdg_surface.set_window_geometry(x, y, w, h)` 之前，它检查宽、高都不为 0，否则 `int3; ud2` 主动崩溃。坐标错位时 QQ 给共享相关的某个窗口算出了空的几何，就撞上这个检查。

不能简单去掉检查：把 0 尺寸发给合成器，wlroots 和 niri 都会按协议报错并断开 QQ（只有 Hyprland 容忍）。`libqq-wl-portal.so` 改的是崩溃桩：把 `int3; ud2` 改写为「弹掉栈上的一项、跳到函数自带的收尾代码」，几何为空时直接返回、不发这个请求，合成器按窗口内容决定大小。

- 只在 QQ 主进程（命令行没有 `--type=`）里做；
- 要求整个函数的字节都对得上（开头、两处检查、跳转目标、收尾代码、填充），且恰好匹配一处，否则不动 QQ、只记日志；
- `--doctor` 会检查 QQ 本体里这段代码还在不在；`QQ_WL_GEOMETRY_FIX_DISABLE=1` 可以单独关掉。

## 附：截图修复（`libqq-screenshot.so`）

QQ 截图前先执行 `echo $XDG_SESSION_TYPE`：是 `wayland` 就走 GNOME 专用的方式（`dbus-send` 调 `org.gnome.Shell.Screenshot`，或用 `gjs` 跑 `screencast.gjs`），否则用主程序里的 X11 代码对根窗口 `XGetImage` / `XShmGetImage` 截全屏。

启动器为了让屏幕共享不被拦截，给 QQ 的是 `XDG_SESSION_TYPE=x11`，于是 QQ 走 X11 这条。而 Wayland 下的 XWayland 是 rootless 的，根窗口没有内容，`XGetImage` 必然返回 `BadMatch`；Xlib 打印错误后返回 NULL，QQ 不检查就去读像素，段错误，按下截图键瞬间闪退。

本库只拦截对根窗口的截取，别的窗口照常交给 Xlib：

- 在 Wayland 会话里，通过 `wlr-screencopy` 逐个截取 Wayland 输出，按 X 的显示器布局（XRandR monitors，名字与 `wl_output` 的名字对应）拼成根窗口坐标系下的整张画面交给 QQ。不能「X 失败了再截」：`XShmGetImage` 在 rootless XWayland 上不报错，只返回全黑；
- KDE（KWin）不实现 `wlr-screencopy`：走 KWin 自己的 `ScreenShot2` 接口拿原始像素（见下一节）；
- GNOME 等两者都没有时，照常调用 Xlib，但临时接管 X 错误（默认处理会直接退出进程），仍然失败就给一张黑图。真正的 X11 会话里截取会成功，行为不变。

截图之后，QQ 会弹出自己的截图窗口，把整张画面当背景让你框选。这个窗口是按「放在桌面左上角、和整个桌面一样大」设计的，Wayland 下程序无法自己指定窗口位置和大小，平铺式合成器会把它当普通窗口平铺，画面按窗口宽度缩放后重复显示。这一点本库没有处理。

> 2026-10-02 补充：修掉了「点 ✓ 后 QQ 闪退」。QQ 把截图放进 Wayland 剪贴板后，Chromium 的剪贴板数据源向粘贴方的管道 `write()` 时没有屏蔽 SIGPIPE；读端提前关闭时，Bugly 会把 SIGPIPE 当致命错误直接杀掉整个 QQ（崩溃日志 `fatalHandler signo: 13`，栈在 `__write`，来自 `ui/ozone/platform/wayland/host/wayland_data_source.cc`）。现在 `libqq-clipbridge.so` 在信号处置层面把 SIGPIPE 强制为忽略（写失败只返回 EPIPE，由 Chromium 自己处理），并加固了读取端：正确处理 `poll` 的 `EINTR`、超时放宽，万一提前放弃也会把 fd 交给后台线程读到 EOF 再关，避免让写端吃到 EPIPE。

### 单屏模式（2026-10-03）

QQ 用 `XGetWindowAttributes(root)` 取「屏幕尺寸」来决定截取范围和截图窗口大小，拿到的却是整个 X 屏幕（所有显示器拼起来的 4530×1440）。平铺合成器里这会让截图窗口横跨多块屏、选择坐标也对不上。

做法：

- hook `XGetWindowAttributes`：根窗口被查询时，把宽高报成**当前聚焦显示器**的尺寸；
- 目标显示器优先问 niri：连 `$NIRI_SOCKET`，发 `"FocusedOutput"`，从 `{"Ok":{"FocusedOutput":{"name":"eDP-1",...}}}` 取名字（1 秒缓存）。不是 niri 或查询失败时退回 `XQueryPointer` + XRandR 显示器矩形；
- 采集时只截该输出（按名字和 `wl_output` 对应），缩放到 QQ 请求的尺寸，于是图像、窗口、选择坐标全程是单屏一致的；
- 注意：XWayland rootless 下指针悬停在 Wayland 原生窗口上时，X 的指针位置可能不更新，所以「指针所在显示器」只能当兜底，niri 的聚焦输出更可靠。

实测日志：

```
[qq-screenshot] single-monitor: report screen as eDP-1 2560x1440
[qq-screenshot] single-monitor: eDP-1 2560x1440 -> requested 2560x1440
```

还有一个小坑：采集路径里 `dlopen("libXrandr.so.2")` 之后 `dlclose`，在进程退出、Xlib 调 `XCloseDisplay` 时会踩到扩展钩子的悬空函数指针而段错误；现在不卸载这个库了。顺带：捕获失败（合成器没有 wlr-screencopy 等）时也走 `capture_free`，不再泄漏 Wayland 连接。

### 缩放输出：上报原生尺寸（2026-10-03）

Hyprland 的 XWayland 把显示器报成**逻辑尺寸**（eDP-1 2880×1800 @ scale 2 → X11 里是 1440×900），而 QQ 的截图覆盖层是 Electron 窗口，缓冲按**设备像素**（2880×1800）。QQ 把逻辑尺寸的截图 1:1 画进 scale 倍缓冲，只填左上角 1/scale（表现为「内容只占左上四分之一 / 重影」）。GNOME/KWin 的 XWayland 本来就报原生尺寸，所以之前没暴露。

修法：`XGetWindowAttributes(root)` 被查询时，顺带轻量查一次 Wayland 输出（`wl_output` 的 mode/scale，5 秒缓存），**统一上报原生模式尺寸**；QQ 的截图请求随之变成原生尺寸，采集 1:1 不再缩放。niri/GNOME（scale 1 或本来就原生）行为不变。

实测（Hyprland，2880×1800 @ scale 2）：

```
[qq-screenshot] single-monitor: eDP-1 scale 2, report native 2880x1800 (x11 1440x900)
[qq-screenshot] single-monitor: report screen as eDP-1 2880x1800
[qq-screenshot] single-monitor: eDP-1 2880x1800 -> requested 2880x1800
```

### KDE 截图：KWin ScreenShot2（2026-10-03）

KWin 不实现 `wlr-screencopy`，但有一套自己的截图 D-Bus 接口 `org.kde.KWin.ScreenShot2`（Spectacle 用的就是它）。它同步返回**原始像素**：`CaptureWorkspace` 把整张工作区写进调用方给的 pipe，附带 `width/height/stride/format`（`QImage::Format`），比 portal 截图（PNG 落盘再解码）快且不产生文件。

麻烦在权限：KWin 会拿调用方 `/proc/<pid>/exe` 去找对应的 `.desktop`，要求里面声明

```
X-KDE-DBUS-Restricted-Interfaces=org.kde.KWin.ScreenShot2;
```

QQ 自带的 `qq.desktop` 没有这一条，直接调会被 `org.kde.KWin.ScreenShot2.Error.NoAuthorized` 拒绝。改 QQ 的 desktop 文件既不归我们管也不可靠，所以本包带了一个小 helper：

- 安装 `qq-screenshot-helper`（`LIBEXECDIR` 下）和 `qq-screenshot-helper.desktop`（`/usr/share/applications`，声明了上面的受限接口）。KWin 按 helper 的 exe 路径匹配，权限检查就能通过；
- `libqq-screenshot.so` 在 KDE 会话（`XDG_CURRENT_DESKTOP` 含 KDE）里 fork/exec 这个 helper，把 helper stdout 的原始像素按 X 根窗口/显示器矩形的比例裁剪、缩放到 QQ 请求的尺寸；helper 的环境里会去掉 `LD_PRELOAD`/`LD_LIBRARY_PATH`，避免把我们的库再注入一次；
- 拿不到像素（权限被拒、KWin 版本太旧、helper 缺失）就照旧退回 `wlr-screencopy`/黑图，不影响「不闪退」的兜底。

一个实测踩到的坑：KWin 读 `X-KDE-DBUS-Restricted-Interfaces` 用的是 `KService::property<QStringList>()`，对 `X-` 键它**不按分号切分**，整段值会作为一个元素参与 `contains()` 精确匹配。所以 desktop 文件里这一行**不能带结尾分号**（Spectacle 也没带）；带了就匹配失败，KWin 回 `org.kde.KWin.ScreenShot2.Error.NoAuthorized`，而且从错误信息上看不出是格式问题。VM 里用 `KApplicationTrader` 复现查询才定位到。

像素格式按 KWin 返回的 `QImage::Format` 处理：`RGB32/ARGB32`（内存里就是 B,G,R,A）直接搬，`RGBX8888/RGBA8888` 交换 R/B 后搬。实测（mock 一个 KWin ScreenShot2 服务，图片按坐标编码颜色）：

```
[qq-screenshot] KDE: captured workspace 4530x1440 via ScreenShot2 (QImage format 4, scale 1.00)
[qq-screenshot] KDE: crop monitor (1970,0 2560x1440) -> image (1970,0 2560x1440) -> 2560x1440
```

裁剪后的每个采样点颜色都与原图坐标公式一致。注意：真实 KWin 的权限检查只能由 KDE 用户实测，mock 验证覆盖的是 D-Bus/pipe/格式/裁剪链路。

关闭：`QQ_SCREENSHOT_KDE=0`（只关 KDE 路径）；`QQ_SCREENSHOT_HELPER` 可覆盖 helper 路径（测试用）。

### GNOME 截图：portal Screenshot（2026-10-03）

GNOME（Mutter）既没有 `wlr-screencopy`，也没有 `ext-image-copy-capture`；它自己的截图是 shell 进程内直接渲染 Clutter stage（`clutter_stage_paint_to_buffer` 等），对应用只开放 portal。所以 GNOME 会话下改走 `org.freedesktop.portal.Screenshot`：

- `qq-screenshot-helper portal` 调 portal（`interactive=false`），等 `Response`（默认 60s，`QQ_SCREENSHOT_PORTAL_TIMEOUT` 可放宽）；
- GNOME 后端第一次会弹它自己的截图对话框（预览+确认），授权后 permission store 记住 app id，**后续截图静默**；KDE 的 portal 后端则始终静默；
- helper 读回落的 PNG（GNOME 存在 `~/Pictures/`），内置最小 PNG 解码器（zlib，8 位 RGB/RGBA）转成 RGBA8888，按同样的「header + 原始像素」管道回传；抓完把文件删掉，避免每次截图在 `~/Pictures` 留文件；
- 库侧按 X 根窗口/显示器矩形裁剪，和 KDE 路径共用同一套逻辑；失败则照旧黑图兜底。

实测（GNOME，2880×1800；首次授权后静默）：

```
[qq-shot-helper] portal handle=/org/freedesktop/portal/desktop/request/1_119/qqscreenshot8497_1 (expected=…)
[qq-shot-helper] portal screenshot file /home/shorin/Pictures/Screenshot-2.png (2885643 bytes)
[qq-screenshot] portal: captured workspace 2880x1800 (QImage format 17, scale 1.00)
[qq-screenshot] portal: crop monitor (0,0 2880x1800) -> image (0,0 2880x1800) -> 2880x1800
image 2880x1800, non-black 100.0%
```

关闭：`QQ_SCREENSHOT_PORTAL=0`（默认仅 GNOME 会话启用）；`QQ_SCREENSHOT_PORTAL=1` 可在其它桌面强制启用（KDE 的 portal 截图是静默的，可当 ScreenShot2 的备胎）。

## 附：观看共享花屏

> 2026-10-02 排查。现象：用 Linux QQ（Wayland 模式）观看别人的屏幕共享时，画面花成横竖黑线；同一路共享在手机、Windows、X11 模式下都正常，摄像头画面也正常。本节记录定位过程和实测日志。

### 结论

QQ 插件解码出的画面和 CPU 帧都是好的。坏在 **Wayland 下 ANGLE 选择了 EGL/GLES 3.0 上下文**：GLES3 删掉了 `GL_LUMINANCE` 纹理格式，而 QQ 插件的 I420 渲染路径正是用三张 `GL_LUMINANCE` 纹理上传 Y/U/V 平面的；ANGLE 需要把 `LUMINANCE` 模拟成 R8+swizzle，这段模拟在 Mesa 上会把纹理数据写坏。换 ANGLE 的 Vulkan/SwiftShader 后端，或改用 X11（ANGLE 走 GLX 桌面 GL，`LUMINANCE` 原生支持），都不经过这段模拟，所以正常。启动器现在会在检测到 Vulkan 时自动加 `--use-angle=vulkan` 规避。

### 证据 1：解码和 CPU 帧正常

QQ 的 AVEngine 日志（`~/.config/QQ/nt_qq_*/nt_data/log/AVEngine.log`）：

```
VideoDecReport strtype:2 senduin:... W:2560 H:1440 ... DecError:0  fps(dout):99 ...
frameCountSendToRender in 10secs = 100, w = 2560, h = 1440, src type = 2.
```

用 gdb 挂在观看端 ppapi 的 `ShareOutput::CopyNormal` / `GLRender::UpdateCallBack` 上，dump 解码平面和打包后的缓冲：

```
COPY render w=2560 h=1440 fmt=1
COPY p0=0x... s0=2560  p1=0x... s1=1280  p2=0x... s2=1280

# 同一帧对比：
decmean/std 64.43/62.54   packedY mean/std 64.43/62.54
mean|diff| 0.000  max 0  frac differing>2: 0.0000
```

即：解码 → `CopyNormal` 重排这一段没有问题。

### 证据 2：与合成器无关，随 ANGLE 后端变化

同一台机器（AMD 780M，niri）观看同一路 2560x1440 共享：

| 配置 | 结果 |
| --- | --- |
| Wayland，默认（ANGLE over GL/GLES） | 花 |
| Wayland，`--use-angle=gl` / `--use-angle=gles` | 花 |
| Wayland，`--use-angle=vulkan` | 正常（GPU 加速） |
| Wayland，`--use-angle=swiftshader` | 正常（软件渲染） |
| X11（`--ozone-platform=x11`） | 正常 |
| 摄像头画面（任意后端） | 正常 |

另外：出问题的窗口里 UI 和摄像头都正常，换成 niri 26.04、DP-2（scale 1.0）也一样花——合成器版本、分数缩放都不是原因。

### 证据 3：探针实测两层 EGL 请求

用一个 `LD_PRELOAD` 探针拦 `dlopen` / `dlsym` / `eglGetProcAddress` / `eglCreateContext`，分别记录 Chromium→ANGLE（前端）与 ANGLE→原生驱动（PROC 层）的调用。

Wayland：

```

eglGetPlatformDisplay(?)
eglBindAPI(EGL_OPENGL_ES_API(GLES))
eglCreateContext: CLIENT_VERSION=3
  display vendor=Google Inc. (AMD) version=1.5 (ANGLE 2.1.26625 git hash: a96fca8d5ee2) client_apis=OpenGL_ES

# ANGLE -> 原生 Mesa EGL（PROC 层）
dlopen(libEGL.so.1)
eglGetProcAddress(eglBindAPI)
PROC-layer eglBindAPI(EGL_OPENGL_ES_API(GLES))
  PROC eglCreateContext: CLIENT_VERSION=3
  PROC eglCreateContext: MAJOR_VERSION=2
PROC eglCreateContext -> ctx=0x... 实际类型=EGL_OPENGL_ES_API(GLES) 版本=3
  PROC display vendor=Mesa Project version=1.5 client_apis=OpenGL OpenGL_ES
```

X11：

```
dlopen(/opt/QQ/libGLESv2.so)
dlopen(/opt/QQ/libEGL.so)
dlopen(libGLX_mesa.so.0)          # 走 GLX
（没有任何 PROC 层 EGL 调用）
eglBindAPI(EGL_OPENGL_ES_API(GLES))

```

两边的前端都请求 GLES3；区别在底层：**X11 下 ANGLE 用 GLX 建了桌面 OpenGL 上下文**（`libGLX_mesa.so.0`，桌面 GL 原生支持 `LUMINANCE`），**Wayland 下没有 GLX，ANGLE 只能向 Mesa EGL 要 GLES3**（实测 `实际类型=GLES 版本=3`），于是必须模拟 `LUMINANCE`。

### 证据 4：没有 Vulkan 时的退化行为

把 `VK_ICD_FILENAMES` 指向不存在的文件，模拟机器没有 Vulkan，再开 `--use-angle=vulkan`：

```
Display.cpp:1097 (initialize): ANGLE Display::initialize error 0: Internal Vulkan error (-9) ...
eglInitialize Vulkan failed with EGL_NOT_INITIALIZED
viz_main_impl.cc:189 Exiting GPU process due to errors during initialization
```

GPU 进程初始化失败后退出，Chromium 退化为软件渲染；QQ 不会崩，但也不再自动回退到别的 GL。所以启动器只在检测到 Vulkan 时才加这个参数。

### 启动器的处理

| 情况 | 行为 |
| --- | --- |
| 默认（`QQ_WAYLAND_FIX_ANGLE=auto`） | 检测到 Vulkan ICD 时加 `--use-angle=vulkan`，否则不加 |
| 没有 Vulkan 且遇到花屏 | `QQ_WAYLAND_FIX_ANGLE=swiftshader`（画面正常，纯软件，较慢） |
| 想完全自己控制 | `QQ_WAYLAND_FIX_ANGLE=vulkan|swiftshader|off` |

`--doctor` 会报告检测结果。检测手段：`/usr/share/vulkan/icd.d/*.json`、`/etc/vulkan/icd.d/*.json`、`$XDG_DATA_HOME/vulkan/icd.d/*.json`（以及 `VK_DRIVER_FILES`/`VK_ICD_FILENAMES` 指向的文件）里有没有 ICD 声明。

### 仍未定位的部分

具体是 ANGLE 的 `LUMINANCE` 模拟上传代码与 Mesa 的哪个交互导致写坏，没有继续下钻：QQ 主程序是 stripped 的，ANGLE 又在 `/opt/QQ/libEGL.so` / `libGLESv2.so` 里（同样是 stripped），没有符号可挂。可以通过 `--disable-angle-features` 关掉的两个 unpack workaround 已实测不是元凶。合适的去处是 ANGLE 上游报告，本文的跨后端对照和两层 EGL 日志可以作为复现材料。

## 附：共享边框窗口

> 2026-10-02 排查与实现。现象：Wayland 下共享屏幕时，QQ 会显示一个标题为「屏幕共享」的全屏窗口；平铺式合成器（niri）把它当普通窗口铺开，共享期间一直占着位置。

### 结论

那个窗口是 QQ 原生代码（标题字符串在 `wrapper.node` 里）通过 Chromium/Ozone 创建的 Wayland toplevel。`libqq-borderfix.so` 在 **socket 层**解析 QQ 出站的 Wayland 线协议，只把这条窗口对应的 `wl_surface.attach(buffer)` 原地改写成 `attach(NULL)`，让它从未映射出来；共享预览和「共享中」工具条（固定尺寸小窗）不受影响。

### 为什么 JS 和符号注入都不行

**不是 Electron 窗口**：

- `app.on('browser-window-created')`、`BrowserWindow.getAllWindows()`，以及 hook `Module._load` 包出来的 `BaseWindow`，全程只看到主窗口 `title="QQ"`；
- 标题字符串 `屏幕共享` 只存在于 `wrapper.node`，`application.asar` 等 JS 包里没有。

**不是 X11 窗口**：`xlsclients` 里没有 QQ，QQ 进程没有 X11 连接；niri 里该窗口的 PID 是 QQ 主进程（走 XWayland 的窗口会显示 `xwayland-satellite` 的 PID）。

**符号拦截不到**：QQ 的 Chromium 静态链接了自带的 Wayland client：

- `readelf -d /opt/QQ/qq`：NEEDED 里没有任何 wayland 库；
- `nm -D /opt/QQ/qq`：既没有引用（UND）也没有定义 `wl_proxy_marshal_*`；
- 但 `strings /opt/QQ/qq` 里有 `wl_compositor`、`xdg_wm_base` 等协议接口名；
- 进程里引用 `wl_proxy_marshal_flags` 的只有 `libgdk-3`、`libwayland-cursor` 和我们自己的库。

实测：把 8 个公开入口（`wl_proxy_marshal[_array][_flags|_constructor...]`）全部 hook 后，主进程里只出现我们自己的剪贴板库那几条请求，QQ UI 的窗口创建完全不经过系统 libwayland。

### 为什么 socket 层可行

不管 client 静态还是动态，Wayland 请求最终都由 libc 的 `sendmsg()` 写进 Wayland socket：

```
QQ 原生代码 / Chromium Ozone（静态 Wayland client）
        │
        ▼
wl_connection_flush → sendmsg(fd, iovec[])
        │  ← libqq-borderfix.so 在这里解析/改写
        ▼
Unix socket（wayland-1）→ 合成器
```

### 线协议与对象链

Wayland 线协议每条消息 = 8 字节头 + 参数：

```
u32 object_id
u32 (size << 16) | opcode        // size 含头，4 字节对齐
参数：i/u/f/object/new_id 4 字节；string/array = u32 长度（含结尾 NUL）+ 内容 + 补齐
```

对象 id 不带类型信息，实现里顺着创建关系推导（opcode 是协议固定值）：

| 出站消息 | 载荷 | 得到的信息 |
| --- | --- | --- |
| `wl_display.get_registry` (1) | `new_id` | registry 对象 |
| `wl_registry.bind` (0) | `name`、`interface` 字符串、`version`、`new_id` | 由接口名知道 new_id 是什么 |
| `wl_compositor.create_surface` (0) | `new_id` | wl_surface |
| `xdg_wm_base.get_xdg_surface` (2) | `new_id`、`wl_surface` | xdg_surface + 对应 surface |
| `xdg_surface.get_toplevel` (1) | `new_id` | xdg_toplevel + 对应 surface |
| `xdg_toplevel.set_title` (2) | `string` | 标题 |
| `xdg_toplevel.set_min_size` (8) / `set_max_size` (7) | `i32 w`、`i32 h` | 尺寸约束 |
| `wl_surface.attach` (1) | `buffer`、`x`、`y` | 上屏缓冲 |

判定「全屏边框」：标题 ==「屏幕共享」且 `min < 600`、`max > 10000`（不设限）。实测：

| 窗口 | min | max | 结果 |
| --- | --- | --- | --- |
| 全屏边框 | 0×0 | 214748364×214748364 | 隐藏 |
| 共享预览 | 202×262 | 202×262 | 保留 |
| 「共享中」工具条 | 87×40 | 87×40 | 保留 |
| 普通窗口 | 0×0 | 9999×9999 | 保留 |

隐藏动作就是把该 surface 的 `attach` 消息第一个参数（buffer id）原地改成 0——xdg-shell 里 `attach(NULL)+commit` 即解除映射；QQ 在第一次 attach 之前就已设好 title/size，所以窗口从未映射出来。

### 实测日志

共享时：

```
[qq-borderfix] hiding 屏幕共享 border window (min 0x0 max 214748364x214748364)
```

期间合成器窗口列表里从未出现 2560×1440 的 `屏幕共享`。只关掉 socket 层做的隔离单元测试（用系统 libwayland 的模拟客户端）同样通过：大框不映射，87×40 浮条和普通窗口保留。

### 踩过的坑

1. **多连接**：一个进程里可能同时有多条 Wayland 连接（剪贴板库一条、QQ UI 一条），不同连接的对象 id 空间独立；最初共用一张对象表，id 互相污染，导致识别不到。现在按连接隔离状态。
2. **`wl_registry.bind` 偏移**：`new_id` 前面还有 `version` 字段（偏移 = `4(name) + 4(长度) + 对齐后的接口名 + 4(version)`）；最初漏了 version，把版本号当成了对象 id。
3. **注入必须卡在消息边界**：曾经在识别到边框后补发 `attach(NULL)+commit`，但当时不确认边界：`sendmsg` 只发出去一部分（或 libwayland 为携带 fd 先单独发 1 字节）时，这些字节会插进一条消息中间，合成器报 `wl_display error 0: invalid object` 并杀死 QQ。现在解析器记录被切断消息的余量、下次跳过，需要注入的消息只在「整块发送成功 + 确认在消息边界」时补发（见 `flush_injection`）。

### KWin 的 explicit sync：只摘 buffer 会崩（2026-10-03）

KDE Plasma 6.7（KWin）上开始屏幕共享会闪退，日志：

```
[qq-borderfix] hiding 屏幕共享 border window (min 0x0 max 214748364x214748364)
libwayland: wp_linux_drm_syncobj_surface_v1#158: error 3: explicit sync is used, but no buffer is attached
```

崩溃 tombstone 是主进程 SIGTRAP（`int3`），RIP 换算成 `qq+0x3a1af2e`，和空几何补丁的桩（`qq+0x39f8225`）不是同一处，说明不是 issue #1。

原因：Chromium 在 KWin 上走 `wp_linux_drm_syncobj_v1`（显式同步）。边框 surface 的每个 commit 都带着 acquire/release timeline point，而我们只把 `attach(buffer)` 改成了 `attach(NULL)`。KWin 的 `LinuxDrmSyncObjSurfaceV1::maybeEmitProtocolErrors()` 在「有 acquire/release point 但没有 buffer」时报 `no_buffer` 协议错误、断开 Wayland 连接，QQ 随之崩溃。旧版（r12）没有 borderfix 所以共享正常；从 0.2.5 起都带 borderfix，所以回退版本也躲不开。

修法：解析 `wp_linux_drm_syncobj_manager_v1.get_surface(new_id, wl_surface)` 建立 syncobj surface ↔ wl_surface 映射；对已隐藏 surface 的 `set_acquire_point` / `set_release_point`（都是 20 字节）原地改写成同一 surface 的 `wl_surface.attach(NULL,0,0)`（同样 20 字节）。这样 commit 里既没有 buffer 也没有同步点，KWin 直接放行；不需要丢消息或压缩缓冲区，消息边界不变。

实测：KDE Plasma 6.7.5 上共享不再闪退、边框窗口照常隐藏；wlroots 系（niri）行为不变。

### 截图覆盖层：标题与全屏（2026-10-03）

截图窗口是 Electron 的 Wayland toplevel：`set_app_id("QQ")`、不设标题、`xdg_surface.set_window_geometry` 是屏幕大小。平铺合成器会把它当普通窗口。本库在 socket 层识别并注入两条完整消息：

- `xdg_toplevel.set_title("QQ 截图")`：Electron 自己不设标题，注入后窗口在合成器里有稳定标题，方便写窗口规则；
- `xdg_toplevel.set_fullscreen`（output=NULL）：让合成器把它精确铺满当前输出。

判定条件：`app_id == "QQ"`、标题为空（未设置或设为空串）、窗口几何 ≥ 600×400。注入按时序要求进行（上一节第 3 条）。实测 niri：

```
[qq-borderfix] requesting title + fullscreen for the screenshot overlay (window 8, 800x600)
```

窗口在 niri 里显示为 `Title: "QQ 截图"`、Tile 2560×1440（全屏）。捕获内容只包含当前聚焦显示器，由截图库的单屏模式（见上一条附录）负责。

### 提示条与麦克风通知（2026-10-03）

进语音等场景下 QQ 会弹一条窄条通知，例如「正在使用"系统默认（Easy Effects Source）"作为您的麦克风」。它是 Electron 建的普通 Wayland toplevel：`app_id "QQ"`、`set_title("提示")`，`set_window_geometry` 是 1200×64 的宽扁尺寸。

本库在协议层同样处理：

- 判定条件：`app_id == "QQ"`、标题 ==「提示」、宽 ≥ 400 且 0 < 高 ≤ 128（尺寸限制避免误伤同名但更大的对话框）；
- 从未映射的：把该 surface 的 `attach(buffer)` 改成 `attach(NULL)`（机制同共享边框）；
- 已经映射过的：补发一条 `attach(NULL)+commit`（走 `flush_injection`，保证在消息边界上发送）。

实测（模拟客户端造一个 `app_id "QQ"`、标题「提示」、1200×64 的窗口）：

```
[qq-borderfix] hiding QQ notification window (提示, 1200x64)
```

niri 窗口列表里从未出现该窗口，同一进程里的普通窗口不受影响。

失败模式：QQ 改标题或尺寸后不再匹配，提示条照旧显示，不影响其它修复。

### 失败模式

标题/尺寸不匹配、接口链认不出来（QQ 改实现）时，代码什么都不做，边框照旧显示，不影响共享本身。整体关闭：`QQ_BORDER_FIX_DISABLE=1`；细节日志：`QQ_BORDER_FIX_DEBUG=1`。

代码是自包含的（[`src/qq-borderfix.c`](https://github.com/SHORiN-KiWATA/linuxqq-wayland-fix/blob/main/src/qq-borderfix.c)，只导出 `connect` 和 `sendmsg`），文件头部有「如何整体删除本功能」的清单。

## 附：屏幕共享改用 NVENC 硬件编码（2026-10-03，实验）

### 结论

QQ 在 Linux 上共享屏幕时，这一路的 H.264 **一定是软件编码**：AVSDK 里没有任何硬件编码器实现，用 NVIDIA 显卡也不会走 GPU。想用 NVENC 只能把 AVSDK 的编码器换掉，本仓库用一个独立的小库 `libqq-nvenc.so` 做这件事，用 `QQ_NVENC=1 QQ_NVENC_ACTIVE=1` 启用。

### 为什么不是「开个开关」就行

- `strings libAVSDKPlugin.so | grep -c 'NV_ENC_|nvenc|NvEncodeAPI|libnvidia-encode'` = **0**：这个库没有 NVENC 代码，它的 H.264 是静态编入的 OpenH264（`o264rt` 包装层，`O264rtCreateSVCEncoder` 等入口都在库里）。
- 共享期间实测 ppapi 的映射：只有 `libAVSDKPlugin.so` / `broadcast-core.so` / Mesa 的 EGL/GL，**没有** `libnvidia-encode.so`、`libcuda.so`。
- `AVSDK_SetHWAbility(mask)` 确实存在（写在 `g_uHwAbility`，还配了 `HardWareEncDetect_*`），但就算把硬件位打开也没有可用的硬件编码器实现，属于死路。
- `broadcast-core.so` 里倒是有一套完整的 NVENC（`NvEncoder_Create` / `NvEncodeAPICreateInstance` / `dlopen("libnvidia-encode.so")`，按 vendor 0x10de 选），但它服务的是 broadcast-core 自己的推流/录制链路，聊天里的屏幕共享不经它。

### 接管点

AVSDK 的编码器接口很小，对象由一个函数指针工厂造出来，所以只需要换掉工厂产物：

```
VENCODER_NS::IVEncoder                       纯虚接口
CO264rtEnc : IVEncoder                       本库唯一实现
CreateH264Encoder(CO264rtEnc **out)          @0xdfce60（导出 GLOBAL）
```

做法是 inline hook `CreateH264Encoder` 的入口（前 14 字节正好是 5 条完整指令，边界干净）：

```
dfce60  55               push rbp
dfce61  48 89 fd         mov rbp,rdi
dfce64  bf 10 02 00 00   mov edi,0x210
dfce69  53               push rbx
dfce6a  48 83 ec 08      sub rsp,8
```

入口写成 `jmp qword ptr [rip+0] -> 我们的工厂`，原实现搬进蹦床（原 14 字节 + 同样形式的跳回），因此原路径随时可用（回落的依据）。

**vtable 下标必须从对象 vptr 数，不能从 `_ZTV` 符号数** —— 对象 vptr 指向的是 C++ ABI 去掉两个表头（offset-to-top + typeinfo）之后的第一个虚函数：

```
_ZTV10CO264rtEnc @0x13f8680:  [0] offset-to-top  [1] typeinfo
  对象 vptr = 0x...8690 ->      [0] ~CO264rtEnc(D1)  [1] ~CO264rtEnc(D0)
                               [2] Init  [3] UnInit  [4] GetErrorCode
                               [5] SetCodecCallback  [6] SetParam  [7] GetParam  [8] DoEncode
```

（第一次把下标按 `_ZTV` 数成 4/7/10，挂钩后行为错乱；用 hooktest 打印对象 vtable 才定死。）

### 结构偏移与输出契约（实测）

```
EncParam:   +0x00 宽  +0x04 高  +0x08 码率(kbps)  +0x0c 帧率
            实测三轮：1200x1920/660k、1920x1088/2700k、2560x1440/3200k，fps 都是 23
VideoFrame: +0x00 宽  +0x04 高  +0x18 Y 行距  +0x1c U/V 行距
            +0x28/+0x30/+0x38 Y/U/V 平面指针（I420；平面间距与 宽*高、宽/2*高/2 完全吻合）
输出:       原实现把编好的帧写进 AVSDK 递进来的 VideoPacket：
              +0x08 帧序号   +0x10 平均 QP   +0x14 长度   +0x18 码流指针
            然后调 SetCodecCallback 收到的回调：
              cb0(SetCodecCallback 的 a, &packet, cb1)
            cb0 = CVideoEncoder::fEncoderDoneCallback @0xd926a0，它读的正是这 4 个字段，
            最终进 CVideoEncoder::CodecDoneCallback(this, data, size, idx, qp)。
            DoEncode 的 VideoPacket 参数就是回调收到的那个对象（帧号/长度/指针都写它）。
```

`SetParam("frame_type")` 值为 1 表示请求一个 IDR；`bitrate`/`fps` 分别用于重配置 NVENC。

### NVENC 侧要点（踩过的坑）

- CUDA 侧用 `cuInit` + `cuCtxCreate_v2` + `cuCtxPushCurrent`，编码会话走 `nvEncOpenEncodeSessionEx(NV_ENC_DEVICE_TYPE_CUDA, ctx)`。
- 编码参数：preset `P4` + `NV_ENC_TUNING_INFO_LOW_LATENCY`，CBR、`frameIntervalP = 1`（无 B 帧、零重排延迟）、`repeatSPSPPS = 1`（原实现每帧都带 SPS/PPS）、`outputAUD = 1`、level 自动。
- **IYUV 输入缓冲里 U/V 平面是半行距（pitch/2），不是整行距**。按整行距推进会越界写：1920x1088 时写出 4.46MB 而缓冲只有 3.34MB，表现为 **ppapi 进程被段错误打死**（日志里表现为 DoEncode 打了「调用前」就再没有任何后续行）。这一点是用独立复现程序定位的，别凭直觉写。

### 验证

- 离线：独立程序（不依赖 QQ）编一帧「上半 Y=64、下半 Y=235、色度 128」，再用 ffmpeg 解码回读，反算流内值与输入一致（注意 ffmpeg 默认做 limited→full 的范围扩张，比较时要换算）；`ffprobe` 认作 h264 / High / yuv420p / level 40。
- 运行时：ppapi 里 `libnvidia-encode` 与 `libcuda` 各有 5 段映射；日志出现 `NVENC: 会话就绪 2560x1440 @23, 3200 kbps CBR` → `NVENC: 出流 73598 字节 qp=34 type=3` → `NVENC 出帧 idx=0 IDR ... -> 回调` → `NVENC: 回调已返回`，两路（1920x1088 / 2560x1440）都在跑，画面正常。

### 回退

不设 `QQ_NVENC` 时该库完全惰性（非 ppapi 进程、以及没设变量的进程都直接返回）；只设 `QQ_NVENC=1` 时仅挂钩旁观、行为与不注入一致；编码过程中任何一步失败都会把该对象标记为 `nv_dead` 并回落原实现，不丢帧。QQ 更新后如果 `CreateH264Encoder` 入口字节变了，挂钩会拒绝执行并在日志里说明，`--doctor` 也会提示。
